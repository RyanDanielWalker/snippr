# Roadmap

*Last updated: 2026-11-12*

This roadmap came out of an October 2026 audit of the code and the live site. The goal is a project that holds up when someone actually clicks the link, reads the code, and asks how it works.

## 1.1.1

1.1 shipped on 2026-11-12, tagged `v1.1` on `2e0da03`, with a [GitHub Release](https://github.com/RyanDanielWalker/snippr/releases/tag/v1.1). The next milestone is three security fixes from Parked ([0051](./adr/0051-close-1-1-and-scope-the-next-milestone-to-three-security-fixes.md)). They're the gaps a reviewer reading the code would most likely find. 0051 called it 1.2. It's 1.1.1, because it fixes things without adding features, and it ends with a version bump, a tag, and a GitHub Release like 1.1 did ([0053](./adr/0053-ship-the-security-milestone-as-1-1-1-with-a-tag-and-a-release.md)). It's done when all four items are ticked.

Everything else is in [Parked](#parked). Parked is a backlog, not a holding pen: anything there can be picked up whenever it's worth doing.

Phases run in order. Items inside a phase can ship in any order. Each item lands as its own small set of commits.

### Phase 7: What a reviewer would find

- [ ] A unique index on `lower(email)`, so the database refuses two users whose emails differ only in capital letters ([0010](./adr/0010-store-emails-lowercased.md)). The app already lowercases emails before saving them; this is the backstop for any path that forgets. One migration, so the commits go to a branch first ([0038](./adr/0038-push-commits-with-a-migration-to-a-branch-first.md)). Two things to settle when it starts. First, production must have no case-only duplicates, or the migration fails during the build. The previous deployment stays live, but Prisma records the migration as failed and refuses every later one until someone resolves it by hand. So Ryan runs a check query in Supabase before the push. It came back empty on 2026-11-12 (query 1 in the [account audit](./audits/2026-11-12-account-links.md)). Run it again just before pushing, since it's cheap. Second, Prisma 5's schema can't describe an index on an expression like `lower(email)`, so the migration is hand-written SQL. Check that a later `npm run db:migrate` doesn't see the index as drift and write a migration that drops it
- [ ] Hash session tokens ([0039](./adr/0039-stop-storing-provider-tokens.md)). `Session.sessionToken` is stored exactly as the browser's cookie holds it, so a leaked row works as a cookie. Stored as a hash, a row is useless without the cookie it came from. NextAuth's adapter methods and `demo-store.ts`, which writes the demo's session row itself, all have to agree on the hashing, so it's bigger than it sounds. Existing sessions are deleted in the same migration, so everyone is signed out once and demos in progress end ([0052](./adr/0052-sign-everyone-out-once-when-session-tokens-are-hashed.md)). How the hashing works needs its own ADR
- [x] Audit the `Account` rows linked before the verified-email check ([0009](./adr/0009-require-verified-email-for-new-accounts.md)). 0009 says a one-off audit would close the gap, and nothing records that it ran. This one reads production, so it's Ryan's step: Claude writes a query that lists each member with the sign-in accounts linked to them, Ryan runs it in Supabase's SQL editor and says whether any link looks wrong. `Account` has no creation date, so the query can't separate links made before 0009 from links made after it. It lists them all, and there are only a handful. Done on 2026-11-12, and clean ([audit](./audits/2026-11-12-account-links.md)). One member has more than one sign-in account, and it's Ryan's own user: the GitHub account matches the one that owns this repo, and the Google account is his own Gmail
- [ ] Move the version to `1.1.1`, tag it `v1.1.1`, and publish it as a GitHub Release ([0053](./adr/0053-ship-the-security-milestone-as-1-1-1-with-a-tag-and-a-release.md)). Same steps as 1.1, in "Releasing a version" in `docs/DEVELOPMENT.md`: one commit for the version and `docs/releases/v1.1.1.md`, then the tag on the commit CI ran on once it has deployed, then Ryan pushes the tag and publishes the Release. Last on this list because it marks the other three as shipped

### Outside the plan

Things Ryan raised on 2026-11-12, after the milestone was scoped.

- [x] Generate failed on saved prompts that list steps. Claude's descriptions were honest but 34 to 39 words, and the check from [0045](./adr/0045-put-the-saved-prompt-rules-in-the-system-prompt-and-check-the-reply.md) turns down anything over 30. The rules now ask for the prompt's goal, not its steps, and start with a verb. Tested against the real Claude: 21 of 21 replies passed, and two injection attempts were described, not obeyed ([0055](./adr/0055-ask-for-a-saved-prompts-goal-not-its-steps.md))
- [x] A card without a description looked lopsided next to one with. Cards in a grid row stretch to the tallest, the code box stopped at 10rem, and the buttons sit at the bottom, so the spare height pooled as a gap between the code and the buttons. Now the code box starts at 10rem and grows into the spare height, showing more code (`SnippetCardView.tsx`, `.snippet-code` in `globals.css`). A side effect: a two-line snippet's box is 10rem tall now instead of shrinking to fit, so every card's code box is at least the same height

## Done

### What 1.0 meant

Snippr is a portfolio piece, and a portfolio piece needs a finish line. 1.0 was that line. It was done when:

- A visitor can try the whole product in one click, on a laptop or a phone, and it looks like someone made choices
- Errors show up in the interface instead of in `alert()` or not at all
- Claude, Cursor, or any MCP client can search and save to your snippet library
- Every push runs lint, typecheck, and tests, and schema changes can't deploy out of order
- Local development no longer touches the production database
- The README explains what was built and why
