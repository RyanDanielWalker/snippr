# 0050. Publish 1.1 as a GitHub Release, with notes kept in the repo

- **Status:** Accepted
- **Date:** 2026-11-11
- **Related:** [0041](./0041-give-1-1-a-version-bump-and-a-tag.md), [0040](./0040-close-1-0-and-scope-1-1-to-two-demo-items.md), `docs/ROADMAP.md`

## In plain English

When 1.1 is tagged, it also gets a GitHub Release: a page on GitHub with a short summary of what changed. The summary is written into the repo first, in `docs/releases/v1.1.md`, so it's reviewed in a commit like everything else. This adds to [0041](./0041-give-1-1-a-version-bump-and-a-tag.md), which planned a version bump and a tag and nothing more.

## Context

Two terms. A *tag* is a name pinned to one commit, so `v1.1` will always mean the commit that shipped 1.1. A *GitHub Release* is a page GitHub builds on top of a tag. It has a title and notes, shows in the sidebar of the repo's front page, and is listed under Releases. The tag already exists in git; the Release is extra, and only on GitHub.

`v1.0` is a tag with no Release, so a visitor to the GitHub repo sees no sign that versions exist, or what any of them contained. The only record of what 1.1 changed is the roadmap and the ADRs, which a visitor has to go looking for.

On 2026-11-11, while checking the public copy before the version bump, Claude asked whether v1.1 should get a GitHub Release, recommended the option below, and Ryan chose it. He didn't give reasons of his own. The reasoning here is Claude's.

## Options considered

1. **Just the tag, as 0041 planned.** Nothing extra to write or keep. The repo's front page shows no versions.
2. **A Release with notes kept in the repo.** The notes are a short Markdown file committed with the version bump, and the Release is published from it with one command after the tag is pushed. It costs one file per release. The notes go through the same review as any commit, and stay in the history if the Release is ever edited on GitHub.
3. **A Release with notes typed on GitHub, or generated by GitHub from commit messages.** Nothing to commit. But notes typed on GitHub skip review, and generated notes for a repo that commits straight to `main` are a list of every commit subject, not a summary.

## Decision

**Option 2.**

- **The notes live in `docs/releases/v1.1.md`.** They're written in the same commit as the version bump. They're plain English, a few short sections: what a visitor would notice, what changed underneath, and links to the ADRs.
- **The Release is published after the tag is pushed.** Ryan pushes the tag, as 0041 says, then runs:

  ```bash
  gh release create v1.1 --title "Snippr 1.1" --notes-file docs/releases/v1.1.md
  ```

  Claude doesn't run it. Like a push, it publishes something, and it needs the tag to be on GitHub first.
- **`v1.0` stays as it is.** No Release is written for it after the fact.
- **This covers 1.1 only,** like 0041. A later milestone decides for itself.

## Consequences

- **Good:** A visitor to the GitHub repo sees that 1.1 exists and what it changed, without reading the roadmap.
- **Good:** The notes are reviewed in a commit and kept in the history.
- **Bad:** One more file to write at release time, and one more command for Ryan after pushing the tag.
- **Bad:** The notes and the Release page can drift if someone edits the page on GitHub. The file in the repo is the one to trust.
- **Follow-ups:** The version-bump item on the roadmap now includes writing the notes and publishing the Release.
