## Findings

Ranked by how much each matters to "an engineer clicks the link and reads the code."

1. **No error page anywhere.** There's no `error.tsx` or `global-error.tsx` under `src/app`. If the database drops a connection while `/dashboard` loads (`src/app/dashboard/page.tsx:17`) or during the demo transaction (`src/lib/demo-store.ts:30`), the visitor gets Next's plain "Application error" screen with no way back. That misses the 1.0 criterion "errors show up in the interface." Small (one `src/app/error.tsx` with a retry). New.
2. **AI search can run twice and answer out of order.** `handleAiSearch` (`src/components/DashboardClient.tsx:119-139`) doesn't check `aiLoading`, and the input stays editable. Press Enter twice: two Claude calls, both counted (a guest has 10 an hour). Search A, then B before A answers: whichever lands last is shown, so A's results can sit under B's text. Turning AI mode off mid-search leaves `aiLoading` true (`:141-146`), so the keyword grid stays hidden behind "Searching with AI..." until the reply arrives (`:406, 432`). Small (ignore Enter while loading, drop stale replies). New; best folded into the Phase 4 AI module.
3. **AI search ignores the open folder.** Results are picked from all `snippets`, not `folderFiltered` (`src/components/DashboardClient.tsx:201-204`), but the folder heading stays (`:348`) and the keyword hint says search only looks in the open folder (`src/lib/empty-state.ts:74`). Open Frontend, AI-search "retry", and "Retry with backoff" from Unorganized shows up under the Frontend heading. Either behavior is defensible; pick one and make the screen say it. Small. New.
4. **Still open, on the roadmap (Phase 4):** no foreign-key indexes (`prisma/schema.prisma:28-50`), bare-id writes (`src/lib/library-store.ts:32, 35, 53, 56`), the rate-limit SQL never runs in a test (`src/lib/ai-usage.ts:19`). One addition: the Parked structured-output item says "today's parsing works," but a fenced or chatty reply silently becomes "nothing matches" (`src/app/api/snippets/search/route.ts:68-74`, described in [0005](../adr/0005-ai-features-as-synchronous-claude-calls.md)) and nothing logs it, so that claim can't be checked. The AI module should log parse failures.
5. **Accessibility basics a reviewer would hit in a minute.** Form inputs are placeholder-only (`src/components/SnippetFormModal.tsx:113-186`); the ✕ and ⋯ buttons have no accessible name (`SnippetFormModal.tsx:108`, `SnippetModal.tsx:85`, `FolderSidebar.tsx:315`); cards announce as buttons but Enter does nothing (`SnippetCard.tsx:78-80`); the preview closes on Escape and the edit form doesn't. Small for labels and names, medium for all of it. Parked.
6. **Worth knowing, no fix needed.** Every save, move, or delete re-runs Shiki on every card, up to 50 (`src/app/dashboard/page.tsx:32`), a cost ADR [0022](../adr/0022-highlight-cards-on-the-server.md) accepts. `src/app/dashboard/page.tsx:17-29` still repeats the store queries. `GET /api/snippets` and `GET /api/folders` still have no caller in the interface. ADR 0022 records two decisions under one title.

Questions an engineer would likely ask:

1. **"How do you stop one user from reaching another's data?"** (`src/lib/snippets.ts:47-60, 114`, `src/lib/folder-ownership.ts:23-32`) Every handler resolves the session, then loads the record and compares its owner before doing anything, including a `folderId` in the body. Missing and someone else's both return 403 so ids can't be probed, and the list queries are tested against real Postgres with two users.
2. **"Why are AI results stored as ids?"** (`src/lib/ai-results.ts:11-17`, `src/components/DashboardClient.tsx:44-45`, [0022](../adr/0022-highlight-cards-on-the-server.md)) The search API returns copies, and `router.refresh()` only updates the page's own snippet list, so a deleted result used to stay on screen. Keeping ids and looking them up in the current list means results follow edits, moves, and deletes, and get the server's highlighting for free.
3. **"Why is there a second `startTransition` inside the first?"** (`src/components/SnippetFormModal.tsx:50-70`, `src/components/FolderSidebar.tsx:126-137`) In React 19, state updates after an `await` inside an async transition aren't part of that transition unless wrapped again. Wrapping the close and the `router.refresh()` keeps "Saving..." up until the refreshed list is on screen, which is also what stopped the folder input from saving twice.
4. **"Why does `DndContext` have a fixed id?"** (`src/components/DashboardClient.tsx:294-298`, [0007](../adr/0007-dnd-kit-for-drag-and-drop.md), `src/components/DashboardClient.test.ts`) Without one, dnd-kit numbers its accessibility ids from a counter that keeps climbing on the server but starts at 0 in the browser, so the two renders disagree and React redraws instead of hydrating. A test renders the page on the server twice to catch it.
5. **"Why highlight on the server?"** (`src/app/dashboard/page.tsx:30-32`, `src/lib/highlight.ts:56-72`, [0022](../adr/0022-highlight-cards-on-the-server.md)) Cards arrive in color and the browser never downloads Shiki for them, only for the preview. The cost is server time on every render and bigger HTML, so it highlights only the first 20 lines and falls back to plain text when Shiki can't.
6. **"How does the rate limiter avoid races?"** (`src/lib/ai-usage.ts:19-25`, [0011](../adr/0011-rate-limit-ai-endpoints-in-postgres.md)) One `INSERT ... ON CONFLICT DO UPDATE ... RETURNING`, which Postgres runs atomically, so two requests can't both read 29. Prisma's `upsert` can split into a read and a write, which is exactly that race.
7. **"Why one sidebar for the phone drawer and the desktop?"** (`src/components/DashboardClient.tsx:310-331`) Each folder is a dnd-kit drop target, and a second copy for the drawer would register every folder twice. So the same component moves with CSS instead.

Clever without an explanation: the nested `startTransition` (question 3). The comments say what it does, not why the second wrap is needed.
